# CBCC AUTHORITY SOURCE PARITY LOCK — v0.6.59

## Problem this lock prevents
CBCC has a long-lived mature baseline plus additive release builders. A release can accidentally ship a current top-level Skill while leaving an older `resources/SKILL.md` behind. Because FULL work is instructed to read the packaged deep authority, that creates ambiguous precedence and allows a future run to consume stale source requirements even when the new release rules are correct.

## Current-release authority invariant
For every packaged release:

1. `plugin.json` semantic version;
2. top-level `skills/cross-border-commerce-creative/SKILL.md` current release version;
3. `skills/cross-border-commerce-creative/resources/SKILL.md` current release version;
4. `skills/cross-border-commerce-creative/resources/VERSION`;
5. latest release builder authority version;

must all refer to the same current release family.

`resources/SKILL.md` is not allowed to remain on an older release while the top-level Skill advances.

## GitHub source model
GitHub `main` is the source of truth, but not every historical root file is the current packaged authority.

- root `SKILL.md` is a **mature baseline source layer** retained for additive construction and historical capability continuity;
- current packaged authority is generated by the latest release builder from the mature baseline + every current master contract / specialist authority;
- the current builder must overwrite the copied baseline `resources/SKILL.md` with the current generated canonical Skill;
- a release overlay that omits `resources/SKILL.md` is invalid when the current installed package contains a stale version.

The root baseline may contain mature detail that remains protected, but its old release number must never be interpreted as the current packaged release number.

## Mandatory pre-release checks
Before publishing or installing a release:

- read `SOURCE_REQUIREMENT_NON_REGRESSION_LOCK.md` and the master contracts it names;
- generate the current canonical Skill;
- write that same current canonical authority to both packaged top-level `SKILL.md` and packaged `resources/SKILL.md`;
- write the same release family to `resources/VERSION` and plugin manifests;
- compare the two packaged Skill files after ZIP/tar creation;
- re-open the actually installed plugin and verify both Skill locations again.

## Failure conditions
Release fails when any of these occurs:

- top-level Skill is current but `resources/SKILL.md` is older;
- `resources/VERSION` and Skill front matter disagree;
- current builder does not overwrite the root baseline copy in packaged resources;
- an overlay update depends on omitted files preserving a stale authority;
- documentation tells the Agent to read `resources/SKILL.md` while that file is not current;
- a release claims source-lock compliance without checking the actually installed plugin.

## Additive guarantee
Authority parity is a packaging/source-resolution rule only. It may not simplify or replace the mature baseline content. The current canonical Skill must remain additive over all protected commercial, strategy, Listing, Asset Universe, Art Direction, people/scene, photography/lighting/CMF/material, Video/Creator/LIVE, QA/Revision and routed Human Workspace capabilities.
