# Final Copy Iteration → Version-Bound Commerce Revision Loop

## Role
Turn authoring/review/performance/VOC feedback into the **smallest versioned copy change that solves the real problem**. Preserve one Strategy Authority while allowing locale/surface copy to improve over time.

## Inputs
Consume when available:
- current locale + field/surface;
- current `version_id` and parent lineage;
- current copy + Chinese delivery companion;
- Product Truth / approved claims;
- field decision job and platform constraints;
- search/keyword role;
- reviewer dimensions and exact feedback;
- Ads / conversion / review-return signals that specifically implicate this field;
- terminology memory.

## Diagnose before revising
Classify the revision reason:
- NATIVE_FLUENCY;
- CLAIM_OR_FACT_ACCURACY;
- PLATFORM_FIT;
- SEARCH_INTENT;
- DECISION_CLARITY;
- EXPECTATION_GAP;
- REDUNDANCY;
- CULTURE_OR_REGISTER;
- PERFORMANCE_HYPOTHESIS;
- TERMINOLOGY_CONSISTENCY.

State the implicated phrase/structure and evidence. Do not rewrite unrelated correct content.

## Revision rules
- Keep specs, numbers, variant identity and claim strength invariant unless the source authority itself changed.
- Preserve useful search coverage unless the revision is specifically correcting search fit.
- Fix the narrowest phrase/ordering problem first.
- When performance is only correlational, frame the rewrite as a test hypothesis rather than a proven cure.
- Do not repeatedly rewrite because a reviewer prefers another personal style if the field already passes its commercial job.
- A new revision always creates a new version; previous approvals do not silently transfer.

## Return
For each revision provide:
- locale / field;
- parent version;
- new version ID;
- exact revised target-market copy;
- Chinese companion meaning/usage when needed;
- revision reason;
- changed span / structural change;
- facts/claims preserved;
- search terms preserved/changed;
- review dimensions requiring re-check;
- performance hypothesis if applicable;
- verification metric / evidence;
- `frozen_correct_content`.

## Release logic
A new version may become `APPROVED_FINAL` only after current-version deterministic checks and independent professional review pass. Stale approval from the parent version must not release the child version.

## Stop rule
Stop iterating when the version is factually correct, native, platform-fit, decision-clear and no material evidence suggests another change will improve the buyer decision. Copy iteration is not an infinite style-polishing loop.
