# Project-Authored Human HTML Delivery Authority

## Core principle
The final `index.html` is a human product interface for the current commerce project, not a visualization of CBCC's internal capability catalog and not a workflow diagram.

The Agent authors the information architecture from the current project's real objects, decisions, surfaces, deliverables and operator needs. Capability names may remain internal routing metadata, but they do not automatically become primary pages or a left-side menu.

## Primary interaction model
- First screen = **project object map**, not a sequence of steps.
- Current priority / next action is a separate focus object; it must not determine navigation order.
- Primary navigation uses current project objects and project-specific labels, e.g. product truth for the actual SKU, the actual market×platform context, the actual locale Listing, current visual world, current asset universe and production objects.
- No fixed sidebar such as Product → Market → Listing → Strategy → Content → Visual → Assets → Prompt → Risk → Sources.
- No numbered 01→02→03 reading implication for strategy/content/evidence unless the business object itself genuinely has an ordered sequence.
- No fixed page count. Empty/inactive capabilities do not create pages. Multiple related objects may share a workspace when that improves real use.
- Different object types use different interaction models: Listing may be a field studio; Visual may be a contact sheet + inspector; Assets may be a portfolio/universe; Strategy may be a decision canvas; Evidence may be a ledger/media wall; one generic card template must not flatten all of them.

## Asset workspace
An asset is one inspectable business/production object, not a phase rail. Design Card, visual execution, photography/CMF when relevant, visible copy, Model Prompt CN/EN, production/assembly notes, QA/source and actual-output repair are lenses on the same asset. They may be entered in any useful order. Do not label them as steps.

## Operator execution
`DO NOW`, launch status or an operator board can exist as a compact focus/drawer, but it must never be injected as the first giant section that pushes the real project down the page. It is a view over underlying objects, not the information architecture.

Likewise, seven-tool continuity, Runtime consumers, hashes, Gate status and capability proofs belong in secondary Inspector/Archive surfaces. They must not be appended as a mandatory human-facing section merely to prove the system has those capabilities.

## Content integrity
Changing the presentation grammar must not remove commercial depth. The project map links to full Strategy, Listing final copy, Visual/Video curation, complete per-asset Design Cards, Model Prompt CN/EN, Visible Copy Blocks, Production/Assembly Notes, Economics/Ads/Review/Evidence when relevant.

## Release rejection conditions
Reject a FULL delivery HTML when any of these is true:
- a fixed capability sidebar is the primary navigation;
- pages imply a universal sequential workflow;
- project objects are reduced to status cards or summaries;
- the operator must open folders/JSON/MD to understand the real work;
- all domains reuse one generic card grid;
- the first screen is an internal runtime/capability dashboard rather than the current commerce project;
- visual/asset detail is hidden behind a thin role/copy/route drawer;
- current priority is confused with permanent information architecture.
